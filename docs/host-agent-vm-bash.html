Capybara · architecture · variant

Host agent + VM bash

Split tools by risk. Declarative file ops (Read/Write/Edit/Glob/Grep) are the SDK's built-in tools running on the host. Arbitrary execution (Bash) runs in a Lima VM with the workspace + granted dirs mounted. The agent process is spawned per turn (--resume <session_id> after the first) and not OS-sandboxed: enforcement is app-layer (a PreToolUse hook + grant store in main). Consent is agent-driven — file tools fail when a path isn't connected, and the model calls request_capybara_directory to ask the user. The BYOK key never enters the agent process: the loopback LLM proxy injects it.

Boundaries

One real boundary, one app-layer policy. The Lima VM contains arbitrary execution (Bash). App-layer (a PreToolUse hook in main + grant store) gates the host file tools. No OS sandbox around the agent on host — the host-side safety is the broker pattern, not the kernel.

Key home

Electron main only (Keychain via safeStorage). The agent's claude subprocess gets a per-turn token; the loopback proxy swaps it for the real key.

Consent flow

Agent-driven, two-step. Built-in tools on a non-connected path are denied by a PreToolUse hook in main with a structured reason. The model calls request_capybara_directory(path, mode) (MCP); main shows a native dialog; on approval the grant store is updated and the model retries.

Grants

Session-only, in-memory in main. Gone when the conversation ends.

Not in scope

No agent-in-VM. No srt around the agent yet — deferred as a future hardening pass once the broker/grant flow is solid (see note at the end).

The shape

A fresh agent process spawned per turn (resumed via --resume <session_id> after the first); one VM for the foot-gun. Granted dirs are exposed to both backends: the SDK built-ins (host) get them after the PreToolUse hook sees the grant, and the VM mounts them in for bash. Main holds only {sessionId, grants} per conversation — no live agent process to track between turns.

A turn — "list the images in my ~/Desktop"

  1. UI → host → spawn host
    Renderer → start-agent-task(prompt). Main spawns a fresh agent process for this turn — first turn of a new conversation, so no --resume; the conversation's grant store starts empty.
  2. Agent tries Glob on ~/Desktop agent
    LLM (via the proxy) decides → calls the built-in Glob({ pattern: "*.png", path: "~/Desktop" }).
  3. PreToolUse hook denies host
    SDK fires the PreToolUse hook in main. The grant store has nothing → the hook returns { permissionDecision: "deny", permissionDecisionReason: "Path \"~/Desktop\" is not connected. Call request_capybara_directory({ path: \"~/Desktop\", mode: \"read\" }) to request access, then retry." }. The model sees the reason as the tool result. No UI appears at this step.
  4. Agent requests access agent
    Per the deny hint, the model calls the MCP tool request_capybara_directory({ path: "~/Desktop", mode: "read" }). Often the model also explains in conversation: "I'll request read access to your Desktop so I can list the images."
  5. Consent dialog on the host host
    The MCP handler in the agent forwards to main; main shows a native dialog ("Capybara wants to read ~/Desktop — Allow / Deny."). On Allow: main adds the path + mode to the in-memory grant store. The MCP tool returns granted.
  6. Retry Glob — now allowed agenthost
    Model retries Glob({ pattern: "*.png", path: "~/Desktop" }). The PreToolUse hook sees the grant → returns { permissionDecision: "allow" }. SDK built-in Glob runs natively in the agent process and enumerates the directory.
  7. Stream the answer agenthost
    Agent formats the list → assistant_message → bridged to the renderer. No bash, no VM hop — pure host file tools.

Why this split

What it buys

  • The foot-gun is off the host. Bash (arbitrary execution) is contained in the VM; the host carries only bounded file ops.
  • Agent-driven consent. The model explains why it needs access in its conversation before the user sees a prompt — clearer intent than a dialog popping out of nowhere.
  • One consent surface. All grants flow through one MCP tool, with one dialog shape, owned by main. The PreToolUse hook is purely a gate, never a UI.
  • Native I/O after grant. Built-in tools run directly on the user's files — no copy-through, no mount tax, no reimplementation of Read/Edit/Grep.
  • Much lighter than agent-in-VM. No Linux claude binary, no in-VM SDK, no host↔VM control channel for the agent. VM is purely a bash runner.
  • Key out of the agent process. Loopback proxy + per-turn token (dies with the process); a compromised subprocess holds nothing reusable.

Honest costs

  • App-layer enforcement on the host. The grant store + the PreToolUse hook gate tool calls. They do not stop a compromised agent process from calling fs.readFile directly, opening a raw socket, or spawning a shell. The host-side safety rests on "no malicious code runs in the agent process." See the note at the end for the future srt hardening pass.
  • Two-step UX on first access to a new dir. Deny → request → retry costs an extra round-trip. Acceptable per conversation; would matter more for high-frequency new-dir access.
  • Granted dirs are exposed to bash too. Bash in the VM can rewrite/delete files inside granted dirs (same exposure as file tools). The VM protects the rest of the host, not the granted dirs from bash.
  • Session-only grants by design. Each new conversation starts empty — the user re-grants as the agent re-asks. Good for least-privilege; some users will find it repetitive.
  • Cross-platform is uneven. macOS / Linux are natural; Windows desktop would need WSL or a redesign for bash.

Future hardening (out of MVP). Three things to revisit once the broker/grant flow is solid: (1) Bash egress in the VM: srt inside the VM around each bash invocation with a domain allowlist, otherwise the VM has open NAT and a clean exfil path. (2) Per-session isolation in the VM: per-session workspace dirs + per-session UIDs (or in-VM srt) so concurrent sessions can't see each other's bash state. (3) Optional srt around the agent on host: an OS-level backstop for the compromised-process case (malicious dep, SDK exploit, etc.). Would require a staging strategy (or accept respawn-on-grant) because srt/bwrap policy is static at launch and our grants are dynamic. KISS-defer until the threat is concrete; the broker pattern is the load-bearing layer, srt would be defense-in-depth. See agent-in-vm.html and llm-proxy.html for the heavier alternatives this builds against.
Architecture variant — sits between Claude Code (Bash on host) and Cowork (full agent-in-VM). The host carries only declarative, bounded file tools gated app-layer by a PreToolUse hook; arbitrary execution lives in the VM; consent is agent-driven via request_capybara_directory. No OS sandbox on the host side — broker and grants are the boundary.
