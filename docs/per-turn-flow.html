Capybara · per-turn flow · current (Electron)

A turn, end to end

Capybara's agent is a one-shot invocation per turn, not a long-running agent process. Each prompt runs the Claude Agent SDK's query() exactly once, in-process inside the long-lived Electron main process, spawning a fresh claude subprocess that runs to completion and exits. It talks to a persistent VM over a persistent supervisor channel — but the agent loop itself is born and dies with the turn.

Agent

One query() per turn. runAgentTask runs once → streams messages → emits task_finished → returns. No loop awaiting the next prompt.

Where

In-process in Electron main. No separate agent process or sidecar — the SDK runs in the host; only the native claude binary is a subprocess (one per turn).

Persists

The Electron main process, the SupervisorClient (VM channel), the cached MCP server, the Lima VM, and the /workspace sandbox state — all survive across turns.

Memory

No cross-turn conversation memory. query() is called without resume, so each turn is a fresh conversation; only the VM filesystem carries forward (see issue #20).

A turn, step by step

  1. UI starts a task uihost
    The renderer calls window.capybara.startAgentTask(prompt) → IPC start-agent-task in electron/main.ts.
  2. Host accepts the turn host
    Main mints a taskId (randomUUID) and an AbortController, tracks it in activeTasks, calls runAgentTask(prompt, taskId, emit, controller), and returns { taskId }.
  3. Ensure the sandbox session hostvm
    Emits task_started, then supervisor.request("create_session", { session_id: "agent_default" }) over the persistent channel — idempotent; prepares the VM /workspace.
  4. Run the one query hostagent
    Builds options (model, system prompt, the capybara MCP server exposing Bash/Read/Glob, allowedTools, abortController) and calls query({ prompt, options }) — once for the turn.
  5. The model reasons agent
    The SDK spawns the native claude subprocess (per query), which talks to api.anthropic.com and decides tool calls.
  6. Tool calls broker into the VM agentvm
    Each Bash/Read/Glob MCP handler calls supervisor.request("run_as_session", { session_id, command, cwd, timeout_ms }); the VM runs it under bwrap as the per-session user in /workspace and returns the result to the model.
  7. Messages stream to the UI agenthostui
    relay() maps SDK messages to agent-event IPC: assistant text → assistant_message, tool_use → tool_use, tool results → tool_result. The renderer renders them via onAgentEvent.
  8. The turn ends agenthost
    The query() stream completes → task_finished emitted → runAgentTask returns → activeTasks.delete(taskId). The claude subprocess exits; nothing of the agent loop persists.

What lives one turn vs. forever

Per turn — born & dies

Created on start-agent-task, gone at task_finished.

  • the runAgentTask invocation + its taskId / AbortController
  • the SDK query() — one per turn
  • the native claude subprocess — spawned by that query

Persistent — survives turns

Spun up once; reused by every turn.

  • the Electron main process — the app
  • the SupervisorClient — module singleton, the VM channel
  • the cached MCP server (cachedMcpServer)
  • the Lima VM + supervisor + /workspace & the agent_default session
No conversation memory across turns. query() is called without resume or an SDK session_id, so each turn starts a fresh conversation with the same system prompt — only the VM /workspace filesystem carries state forward. SESSION_ID = "agent_default" is the VM sandbox session, not the SDK conversation. Threading the SDK session_id + resume to give real cross-turn memory is tracked in issue #20. For where the agent runs relative to the trust boundary, see agent-in-vm.html.
