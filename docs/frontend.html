The renderer — React UI probe harness

A single-window React app (Tier 1 of the architecture) that drives the agent and shows what it does. Today it's a deliberately thin probe over the window.capybara bridge; the real conversation UI is sketched at the end.
Renderer = Chromium, sandboxed, no Node · talks to Electron main only through window.capybara (contextBridge) · source under src/

At a glance

The renderer is a Vite + React 19 app loaded by Electron from dist/index.html. It has no router and no global store — three components, each holding its own useState, all data crossing the process boundary through the typed window.capybara surface. It exists to exercise the host/VM/agent stack end-to-end: type a prompt, run a task, watch the raw event stream. It is not (yet) a polished chat product — the transcript is JSON, newest-first, capped at 20 events.

App.tsx — <main> flex column, centered, no router
<Settings /> — gear dialog · BYOK Anthropic key (get/set/remove)
<VmStatusPill /> — 🟡 starting · 🟢 running · 🔴 failed(reason)
<AgentProbe /> — prompt input · Run · resume toggle · JSON event transcript

The components

AgentProbe.tsx — the task surface

The one screen that matters. State (all local):

const [prompt, setPrompt]       = useState("Organize my Downloads folder");
const [busy, setBusy]           = useState(false);
const [events, setEvents]       = useState<string[]>([]); // JSON-stringified, newest-first
const [error, setError]         = useState("");
const [sessionId, setSessionId] = useState<string | null>(null);
const [resume, setResume]       = useState(true);
  • Subscribe once, on mount. subscribeAgentEvents(cb) returns an unsubscribe fn (returned from the effect). On each event it captures sessionId from session_started and prepends the JSON to events, sliced to 20: [JSON.stringify(event, null, 2), ...prev].slice(0, 20).
  • Run. startAgentTask({ prompt, resumeSessionId: resume && sessionId ? sessionId : undefined }). The call returns a { taskId }; the actual output arrives asynchronously over the event subscription, not as a return value.
  • Conversation continuity. The "Continue conversation" checkbox decides whether the captured sessionId is passed back as resumeSessionId on the next run. "New conversation" clears sessionId + events.
  • Render. a <pre> of events.join("\n\n") (or "(no agent events yet)"), plus a red <pre> for any thrown error.

VmStatusPill.tsx — boot indicator

Shows the Lima VM's lifecycle. Races a live subscription against a one-shot fetch so it never flashes stale state: 

const unlisten = subscribeVmStatus((next) => { receivedEvent = true; setStatus(next); });
getVmStatus().then((current) => { if (!receivedEvent) setStatus(current); }); // fetch loses to events

Renders a colored pill: starting → 🟡, running → 🟢, failed → 🔴 with the reason in a scrollable <code>. The agent can't usefully run until this is green (main's getSupervisor() requires the VM booted).

Settings.tsx — BYOK key

A gear-icon dialog (shadcn/radix Dialog). On open it calls getSettings() → ApiKeyState { hasApiKey, apiKeyPreview, unreadable }; the input placeholder shows the stored preview. Save calls setAnthropicApiKey(key) (passing "" removes it) and echoes the returned state; an eye icon toggles reveal; a "Remove" button appears when a key exists. unreadable (keychain unlock failed) gets its own message. The key itself never lives in the renderer — only the boolean + a short preview.

The bridge: window.capybara

The renderer's only door to main, exposed via contextBridge in electron/preload.ts and typed in src/lib/host.d.ts. Thin per-domain wrappers in src/lib/{agent,vm,settings}.ts forward to it and re-export the types, so components import startAgentTask rather than touching window.capybara directly.

Method Shape Wrapper
startAgentTask ({ prompt, resumeSessionId? }) → Promise<{ taskId }> lib/agent.ts
onAgentEvent (cb: (AgentEvent) => void) → unsubscribe lib/agent.ts
getVmStatus / onVmStatus () → Promise<VmStatus> / (cb) → unsubscribe lib/vm.ts
getSettings / setAnthropicApiKey () → Promise<ApiKeyState> / (key) → Promise<ApiKeyState> lib/settings.ts

The AgentEvent stream

A task's output is a sequence of these (relayed from main's runTask.ts over webContents.send). The transcript is just this stream, accumulated: 

type AgentEvent =
  | { event: "task_started";    taskId }
  | { event: "session_started"; taskId; sessionId }   // ← captured for resume
  | { event: "assistant_message"; taskId; text }
  | { event: "tool_use";    taskId; tool; input; toolUseId }
  | { event: "tool_result"; taskId; toolUseId; content; isError }   // pairs with tool_use by toolUseId
  | { event: "task_finished";   taskId; sessionId? };

Note what the UI doesn't do with these yet: tool_use and tool_result share a toolUseId but aren't paired visually; assistant_message.text is shown as JSON, not markdown; there's no running/finished affordance beyond the events themselves.

One task, end to end

The key mental model: startAgentTask is fire-and-subscribe. Its promise resolves to a { taskId } the instant main accepts the request — the actual work streams back later over the onAgentEvent subscription, not as a return value. A renderer-eye view of one run:

  1. Run. runAgent() calls startAgentTask({ prompt, resumeSessionId }) → contextBridge → ipcRenderer.invoke("start-agent-task").
  2. Main accepts. Assigns a taskId, attaches an AbortController, kicks off runAgentTask(…), and returns { taskId } immediately. The renderer just flips busy off — it holds no task handle.
  3. Events stream. As the in-process agent emits messages, main relays AgentEvents via webContents.send("agent-event", …). The mount-time subscription fires once per event.
  4. Renderer accumulates. Each event is prepended to the transcript; session_started stashes the sessionId (the only event the UI treats specially).
  5. Done. task_finished closes the turn. The captured sessionId, if "Continue conversation" is on, rides the next startAgentTask as resumeSessionId.

Consequence of holding no task handle: there's nothing to cancel or reconcile if the user navigates or re-runs mid-task — see the Stop-button item below. The fuller cross-tier sequence (main → VM → supervisor) lives in architecture.html and per-turn-flow.html.

Proposed direction — a conversation UI, learning from Slack & Telegram

Today's AgentProbe is a debug surface; the goal is a focused agent conversation UI. Slack and Telegram desktop have spent a decade solving "a fast, legible message stream in a desktop window" — so borrow their proven patterns rather than reinvent. But adapt, because Capybara isn't team chat: there's one agent, not a room of people; the "senders" are agent / tool / system; and the interactions are permission prompts, not reactions and presence.

What transfers, and what doesn't:

  • Drop (no fit): avatars, presence dots, reactions, @-mentions, multi-room unread math — one agent, one user.
  • Repurpose (great fit): Slack's thread pane → a tool-call detail pane; Telegram's centered "service messages" → agent lifecycle events; Telegram bots' inline keyboards → the folder-consent buttons.

Shell — three panes (Slack)

Slack's left-rail / message-pane / right-detail split is the right desktop shell. Map it to: left = conversation history (keyed by sessionId, a ⌘K quick switcher, ⌘N new); center = the transcript; right (collapsible) = conversation info — granted folders, session id, model, live VM status.

└─────────────┴──────────────────────────────────┴───────────────┘

Transcript — turns, not a JSON dump

  • Group by turn (Slack message grouping). One assistant turn's assistant_message text + its tool calls render as a single timestamped block, not interleaved raw events. Back it with a real model (messages[] + a Map<toolUseId, ToolCall>), not a capped string array.
  • Markdown, streamed (both). Render assistant_message.text as markdown as it arrives, with a "working…" indicator between task_started and task_finished; auto-scroll with a Slack-style jump-to-latest pill when the user has scrolled up.
  • Service messages (Telegram). Lifecycle and system events — session_started, task_finished, "Granted ~/Desktop", VM transitions — render as centered, muted "service" lines, the way Telegram shows joins/pins. This is what replaces the raw JSON event dump.

Tool calls — cards, detail in the side pane (Slack threads)

  • Pair tool_use ↔ tool_result by toolUseId into one collapsible card: tool name, a spinner until the result lands, a host vs VM badge (a Bash card ran in the VM; a Read card on the host — the trust boundary made visible), and an error state from isError.
  • Clicking a card opens its full input/output in the right pane — the same move as opening a Slack thread, so detail never clutters the main flow. Code/file output gets syntax highlighting, collapse, and a copy button (Slack code blocks).

Consent — inline action buttons (Telegram bot inline keyboards)

The path-gating deny → request_capybara_directory → grant loop (path-gating.html) today pops a native OS dialog. Telegram bots already solved "a bot asks the user to choose" with inline keyboards — buttons attached under a message. Render consent the same way: 

◆ Capybara wants to access  ~/Desktop
                            [ Allow ]   [ Deny ]

In-flow, dismissable, and it keeps the granted-dirs list in the right info pane. This is the one place the model fits an agent better than team chat does — the agent asks, like a bot.

Composer & feel (Slack / Telegram)

  • A real composer: multiline input pinned at the bottom, Enter to send / Shift+Enter for a newline, a Stop button while a task runs, and slash commands (/new, /resume, /model) echoing Telegram's bot command menu.
  • Telegram's restraint: fast and low-chrome — virtualize long transcripts, smooth scroll, instant interactions, nothing heavier than the content. Plus the in-app dark-mode toggle (#25) and model selection in Settings.

Cost to get there: most of this is pure renderer work over the existing event stream — no main changes. Only two pieces need the bridge: a cancelAgentTask(taskId) for the Stop button, and surfacing the consent request to the renderer (so the inline buttons can replace the native dialog).
