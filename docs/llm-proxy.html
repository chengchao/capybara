Keep the BYOK key out of the agent

With BYOK the Anthropic key is the user's own, stored encrypted on their machine (Keychain via safeStorage, #30) — so it's fine for the key to live on the client. The one rule: the agent must never see it. Today the decrypted key is handed straight into the claude subprocess. This change inserts a loopback proxy in Electron main that holds the real key and hands the subprocess only a disposable token.

Boundary

Trusted host vs. untrusted agent — on the same machine. Not client vs. server. The key stays on the client; it just stays out of the agent.

Key home

Electron main only. Decrypted from safeStorage at request time, held by the proxy, never written to the agent's env.

Agent holds

A random per-run token as its x-api-key, plus an ANTHROPIC_BASE_URL pointing at the loopback proxy.

Not in scope

No remote backend, no key custody service, no VM-egress lockdown, no moving the agent into the VM — those are separate follow-ups.

Before → after (the key's path)

Today (#30)

The decrypted BYOK key is injected straight into the agent's subprocess.

  • main decrypts the key (safeStorage)
  • env: { …, ANTHROPIC_API_KEY: realKey } → the claude subprocess
  • subprocess calls api.anthropic.com directly
  • the subprocess holds the real key — a compromised binary/dep leaks it

After (proxy)

The key never leaves main; the agent gets a token.

  • main decrypts the key (unchanged)
  • env: { …, ANTHROPIC_API_KEY: token, ANTHROPIC_BASE_URL: loopback }
  • subprocess → loopback proxy → api.anthropic.com
  • proxy swaps token → real key — subprocess holds only a token

The shape

One process, one boundary: the real key lives only in Electron main (blue). The agent subprocess (green) is handed a token and a loopback URL; the proxy is the single, Anthropic-only exit. 

  ┌─ Electron main · TRUSTED · decrypts BYOK key (safeStorage) ─────┐
  │                                                                 │
  │   loopback proxy  127.0.0.1:<port>                              │
  │     x-api-key == token ?  → swap in real key →  forward/stream  │ ──► api.anthropic.com
  │          ▲                                                      │

Why & what's out of scope

What it buys

  • Defense-in-depth. The decrypted key never enters the subprocess that runs the model loop; a compromised binary/SDK/dependency leaks a useless token.
  • Agent-in-VM groundwork. This is exactly the mechanism the in-VM agent needs (key on host, agent holds a token) — built once, no rework.
  • Anthropic-only egress. The proxy's single fixed upstream can't be turned into an open relay.

Honest scope

  • Not closing an open hole today. The model is already confined to VM-only tools, so it can't read main's or the subprocess's env right now. This hardens the runtime, not a live leak.
  • Agent stays in-process. Main still holds the key and runs the agent, so an RCE in main still reaches it — the full payoff needs the agent-in-VM move.
  • No remote server. BYOK = the user's key on the user's machine; no custody backend.
Two runtime unknowns to confirm on first real run (don't change the design): (1) the claude binary accepts an http:// loopback ANTHROPIC_BASE_URL — Anthropic SDKs normally allow http for localhost; (2) the SDK env is spread over process.env then overridden, so the subprocess keeps PATH/HOME and the real key is replaced by the token regardless of merge-vs-replace semantics. See agent-in-vm.html for the larger design this is a step toward.
